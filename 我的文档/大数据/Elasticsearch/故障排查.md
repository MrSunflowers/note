# 排查 JVM 内存压力过高问题

Elasticsearch 的 JVM 使用了 G1GC 垃圾收集器。随着时间的推移，这会导致 JVM 堆内存使用量指标呈现出一种锯齿状模式，由于这是一个瞬时测量值，它会导致报告的堆内存百分比产生波动。您应该将监控重点放在 JVM 内存压力​上，而不是某一时刻的内存使用值。因为这个百分比是你查询监控那一瞬间的值。你可能在“锯齿”的顶峰（比如 85%）查到，也可能在谷底（比如 30%）查到。单看一个点，无法判断系统真实状态。

正确的方式是监控“JVM 内存压力“，这是一个滚动平均值，它计算的是老年代（Old Generation）空间在垃圾回收中花费的时间比例。你可以把它理解为 GC 的“工作强度”。它不是一个瞬间快照，而是一段时间内（如最近 15 分钟）GC 忙碌程度的平均反映。它直接关联到 JVM 的“响应能力”。如果 GC 一直在拼命工作（高压力），那留给应用程序（处理你的搜索/索引请求）的 CPU 时间就少了，节点就会变慢、延迟增高。

假设你在你的 Ubuntu 24.04 服务器上部署了一个 Elasticsearch 节点，并通过 _cat/nodes?vAPI 或监控工具（如 Elastic Stack 的 Monitoring、Prometheus+Grafana）查看状态。

你运行命令查看节点状态，发现 heap.percent 这一列显示为 78%。这是一个瞬时测量值，并不能反映此时 GC 的真实工作负载。实际上，你通过 Elasticsearch 的监控 API 或集成好的 Grafana 看板，找到了 jvm.mem.pressure​ 这个指标。它的值是一个 0 到 1 之间的小数（或 0% 到 100%）。这个才是要关注的综合指标。

场景 A：heap.percent在 40%-80% 剧烈波动，但 jvm.mem.pressure稳定在 0.1 (10%) 左右。

这是非常健康的状态！剧烈的 heap.percent波动正是 G1GC 正常工作的“锯齿”表现。低内存压力说明 GC 很轻松，没有花费太多时间，节点响应迅速。

场景 B：heap.percent持续高于 90%，jvm.mem.pressure持续高于 0.75 (75%)。

这是真正需要警报的状态！高堆内存占比结合高内存压力，说明老年代里可能充满了难以回收的对象（可能是内存泄露，也可能是你的数据负载确实超过了当前堆内存的合理容量）。GC 在拼命工作但效果不佳，节点响应会非常缓慢。
